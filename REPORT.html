00

What came out of it

  1. 01

    Mel-mode checkpoints could not be evaluated at all. Every eval decoded audio, which on this machine exists only as .tar archives. build_chroma --mel-root now embeds straight from the precomputed .npy spectrograms; the three DB-only evals needed no changes.

  2. 02

    The model was never meaningfully worse than FMA. That comparison was invalid twice over — the old baselines came from a corpus with ~8× fewer labels, and the genre metric was scoring against the alphabetically-first tag. On clean labels the model scores 0.410–0.438, inside the historical 42–46% band.

  3. 03

    Three of the four levers the project's own notes pointed at are dead ends, measured rather than argued: the augmentation chain, the mel resolution, and lambd. Epochs are the only confirmed lever.

  4. 04

    The bottleneck is the objective, not a hyperparameter. Barlow Twins pulls two views of one track together and decorrelates dimensions, but never pushes different tracks apart. A 5 s window's nearest neighbour is its own track only ~0.41–0.44 of the time, and whitening barely helps — so it is not a geometry problem.

01

Issues faced

The blocker: no way to score a mel-mode run

Training reads precomputed log-mel .npy files (~/mtg_jamendo, 32,783 tracks). Every eval path decoded audio, and this machine has no unpacked audio — only raw_30s_audio-low-*.tar, with no cached_mtg/. So a mel-mode run's quality was unknowable: the train CSV told you the loss descended, never whether the embedding was any good.

The .npy ↔ metadata join was documented wrong

Project memory said the .npy ids are MTG track ids. They are not: a stem is a bare integer (214.npy) while a TSV TRACK_ID is track_0000214. The number also appears in the TSV PATH column as <num%100:02d>/<num>.mp3, matching the directory layout. The join is int(TRACK_ID.split("_")[1]).

autotagging.tsv is a symlink to a curated subset

It points at raw_30s_cleantags_50artists.tsv, which omits 65 of the 32,783 melspec tracks. Joining naively would either drop those 65 — making the eval corpus a strict subset of the trained one — or give them blank metadata, putting an empty genre into the k-NN majority vote. Fixed with a fallback to the full raw_30s.tsv for exactly the missing numbers.

The existing chroma_db/ was FMA-era, not MTG

CLAUDE.md claimed the DB had been rebuilt with MTG embeddings. On inspection it held 7,916 FMA tracks: every row carried the FMA listens key and FMA genres (Hip-Hop, Pop), not MTG's (punkrock, gospel). The docs asserted a rebuild that had not happened. Git cannot settle the baseline table's provenance either — the table and every FMA reference arrive together in one squashed commit carrying that same false claim.

Consequence: the historical baselines are unusable for comparison, and that DB has since been overwritten — so it cannot be re-measured.

Chroma's upsert merges metadata instead of replacing it

Rebuilding over the FMA DB left the FMA listens key on exactly rows 0–7915 — the old DB's extent — while every shared key took the correct MTG value. Harmless for the evals, which read only shared keys, but it means a rebuild-in-place is not identical to a fresh DB. Separately, a run covering fewer tracks than the last leaves surplus vectors behind.

Several GB of avoidable Python floats

build_chroma materialised per-window embeddings with .tolist(), and db.load_all accumulated every page as Python floats. At 163,915 × 128 that is roughly 670 MB of boxed floats on a box with ~3 GB free. Both now pass float32 numpy arrays. Measured peak RSS is flat at ~1.6 GB from 100 → 3,000 tracks — fixed runtime overhead, not data-proportional.

Operational hazards

  • train.py writes checkpoints relative to the cwd, so a run started from the repo root silently overwrites checkpoint_e0…. A 17-epoch ablation would have destroyed e0–e16. Experiments now run from ~/mel_runs/<tag>/.
  • Background jobs were killed mid-run — twice, including one 100-epoch attempt at epoch 0. Not OOM; GPU and RAM were clean. Fixed by launching with setsid nohup, which the repo's own launch script already recommends.
  • The LR schedule is inert. Over 43 epochs the reference run's lr never left 1e-4 — ReduceLROnPlateau(patience=10) never fires, because the loss keeps inching down ~−1/epoch on a loss of ~627. The model was never annealed.
02

Corrections — including to my own work

My lambd conclusion was confounded by epochs self-correction

I found train.py's --lambd default (5e-2) contradicting the docs (which said 2e-2 in one place and 3e-3 in another, while instructions.md §5 recommends 2e-3–5e-3), and that at e42 off_diag was 38% of the objective while the mean off-diagonal correlation was already only |c| ≈ 0.067. A harness sweep showed on_diag falling 83 → 2 as λ dropped, and I concluded the default was a real misconfiguration.

That was wrong. I had compared λ=5e-2 at 42 epochs against the others at 17. At matched 17 epochs all three are identical on retrieval. And I was optimising on_diag, which is not a valid proxy.

on_diag is not a valid proxy for the objective method

on_diag falls 447 → 334 → 228 across λ = 5e-2 → 2e-2 → 5e-3 with no retrieval benefit whatsoever (0.3453 / 0.3520 / 0.3553, within sampling noise). Mechanism: off_diag — redundancy reduction — is what spreads the embedding cloud. Lowering λ removes that pressure, the cloud contracts, and the two views of a track move closer, which is exactly what on_diag measures, while different tracks crowd together.

It remains useful for its original job: spotting a config whose two views share too little signal to learn at all (pinned near ~800–1000 ≈ D). Real changes should be judged on retrieval and the collapse count. I corrected instructions.md §9 and CLAUDE.md rather than leaving the wrong version standing.

The genre metric was measuring the alphabetically-first tag metric bug

82% of the corpus carries 2–9 genre tags, and the TSV stores them in alphabetical order. So tags["genre"][0] — which test_knn had always scored against — means "the alphabetically first genre". track_0000946 is ambient, chillout, downtempo, easylistening, electronic, lounge and was labelled ambient because 'a' < 'c'. A neighbour sharing a genuine genre under a different first letter scored as wrong, deflating accuracy on ~80% of the test set. This is the single change that most moved the headline number — and it moved it up.

db.py never actually sorted by window latent bug

The docstring promises ordering by (track idx, window), but the code parsed the window as split("_")[3] for ids shaped track_<idx>_w<k> — whose split is ['track', '<idx>', 'w<k>'], three elements, so the branch never ran and window was always 0. Fixed, and verified to produce identical eval numbers, so no recorded figure is invalidated.

Stale documentation corrected docs

  • CLAUDE.md described the conv stack as 3 blocks ending in AdaptiveAvgPool2d(1); model.py has 4 blocks ending in AdaptiveAvgPool2d(2) → 512 features.
  • CLAUDE.md's lambd note quoted three different values across two places.
  • CLAUDE.md's chroma_db claim, memory's .npy-id claim, and test_network.py's reference to a listens key MTG does not have.

Bugs in my own throwaway tooling self-correction

  • The chain-ablation harness fed CPU tensors to a CUDA model. Under autocast that raises a misleading Input type (float) and bias type (c10::Half) instead of a device error, which cost several debugging rounds. The repo code was never affected.
  • A monitor's pgrep pattern was malformed, producing a false "process died" alarm.
  • The retrieval script parsed the window index with the same wrong split as the db.py bug above.

Read the collapse counts as indicative, not precise

off_diag varied by ~29% between two runs of the identical config (6,181 vs 4,806 at the same epoch), and single-run collapse spanned 42–209 per 1,000. That is why the λ decision leaned on retrieval (1,500 sampled queries, ±0.03 noise) rather than collapse.

05

The finding that matters

test_retrieval.py asks the question the model exists to answer: for a 5 s window, does its nearest neighbour belong to the same track?

Same-track retrieval · e42 · 1,500 sampled queries
Neighboursrawwhitened
top-10.43530.4400
top-30.51400.5260
top-50.54270.5620
top-100.58200.6093

Chance is 2.4e-05 — the model is ~18,000× above it, but a Shazam-style fingerprint wants top-1 near 1.0. And whitening barely moves it, unlike the intra/inter gap, where whitening transforms the result. That combination is diagnostic: the weakness is not poor conditioning and not any hyperparameter tested. It is structural.

Barlow Twins (i) pulls two views of the same track together and (ii) decorrelates dimensions. It never pushes different tracks apart. Redundancy reduction is not instance discrimination — which is why raw inter-track similarity sits at 0.80–0.86 while genre k-NN looks respectable.

Levers ruled out, with evidence

LeverVerdictEvidence
Augmentation chain dead end Removing every content distortion and RRC moves on_diag only 97 → 73 (~25%); λ moves it 40×. instructions.md §8 had named the chain "the remaining knob" — now refuted. No augmenter.py change was made.
n_mels 96 dead end Equal to 64 on genre (0.305 vs 0.302), worse raw collapse (0.8610 inter vs 0.7956). The bilinear 96→64 merge costs nothing.
lambd a wash Identical on retrieval at matched epochs; a trade elsewhere — lower λ: +0.03 genre, worse collapse.
Epochs confirmed Retrieval 0.35 @ 17 ep → 0.435 @ 42 ep.

Next lever: the objective. Add a contrastive / InfoNCE term (or VICReg-style variance + invariance) so different tracks are explicitly repelled. After that, LR annealing — since the current schedule has provably never fired.

Reproducing

# score a mel-mode checkpoint (the port this work added)
nix develop . --command python -m music_encoding.build_chroma \
    <ckpt>.pt --mel-root ~/mtg_jamendo \
    --mtg-data ~/mtg-jamendo-dataset/data --n-mels 64
nix develop . --command python -m music_encoding.test_knn
nix develop . --command python -m music_encoding.test_similarity_same_song
nix develop . --command python -m music_encoding.test_retrieval
nix develop . --command python -m music_encoding.test_network --color genres

--n-mels must match the training run. The conv stack is resolution-agnostic, so a mismatched value runs fine and silently returns wrong numbers — nothing can validate it for you. And do not launch a training run from the repo root unless you intend to replace checkpoints/.
